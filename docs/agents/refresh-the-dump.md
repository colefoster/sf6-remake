# Refreshing the dump from a live game

## Where the two trees stand

`data/raw/mmdk/` is a dump taken **off the running game** — 24 fighters, the
Aug-2026 build, stamped `live-2026-08-19`. ADR-0045 re-pinned onto it.

`data/raw/mmdk-2024/` is the third-party snapshot the pipeline used to read:
`alphazolam/MMDK` at `831564f`, whose last commit is 2024-12-06. It is what
`fetch-mmdk.mjs` downloads (`npm run geometry:2024`), and it exists so the audit
below can still be run. **Do not point the fetcher at `mmdk/`** — re-dumping the
live tree needs the game running and a human at the pad.

So a disagreement `sf6 verify` reports still has two possible causes — our
reading, or the two sources being out of step — but the second one is measured
now, and it runs **both ways**: FAT lags the live game on 49 rows. See
[ADR-0043](../adr/0043-version-skew-is-worth-half-a-point.md) and
[ADR-0045](../adr/0045-the-dump-is-the-live-game-now.md).

## The atemi table is a separate button

MMDK's character dump has no atemi table, which three ADRs were written around.
Its **Dump Atemis** button does: `common_atemi.json` at the dump root, plus
`<Char>/atemi.json` for the fighters with private rows (Luke, Marisa, Zangief).
Press it while you are in there — `extract-geometry.mjs` reads both layers if
they are present and falls back to ADR-0039's FAT-derived hit counts if they are
not.

An atemi **index is only meaningful with the table from its own build**. Between
the pinned snapshot and the Aug-2026 dump, Luke's Sokutou moved from row 6 to 5
and Zangief's 5HP from 6 to 7. Pasting one dump's table onto another's geometry
resolves armor onto the wrong row — silently, and in Zangief's case onto a row
that takes no damage at all. See
[ADR-0042](../adr/0042-the-atemi-table-was-behind-another-button.md).

## The other two shared dumps

Beside **Dump Atemis** there is a rects dumper: `common_rects.json` at the dump
root, the shared rect tables that sit behind every fighter's own. It carries the
downed-state pushbox (`BoxNo` 6) that no fighter's tables have and that the
extractor warned about for two years — press it too. See
[ADR-0046](../adr/0046-the-shared-rect-tables-and-the-box-a-downed-fighter-has.md).

`common_moves.json` writes `null` on this build. It dumps nothing; do not go
looking for shared action data in it.

## Who cannot be dumped, and why

Both trees hold the same 24 of FAT's 30. Absent: **Alex, C.Viper, Elena, Ingrid,
Mai, Sagat** — plus **Yasmine**, who FAT does not publish either. They are
excluded from every geometry-based check and cannot be played in the runtime.

This is not a missing asset. MMDK's roster is a **hardcoded table** in
`MMDK/reframework/autorun/MMDK/tables.lua`:

    characters = { [1]="Ryu", ... [22]="Akuma", [26]="M Bison", [27]="Terry" }

keyed by the game's internal character id, with 23/24/25 unaccounted for. Anyone
released after Terry has no entry and therefore **no box in the dumper's UI**.
Upstream has not moved since 2024-12-06, so adding them means adding a line per
fighter — and the blocker is knowing each new fighter's internal id, not the
dumper.

## Getting a live dump

MMDK does not read files off disk. It is a REFramework Lua script that dumps
the deserialized `CharacterAsset` objects **out of the running game**, so a
human has to launch SF6 and drive its UI. There is no headless path.

Extracting from `re_chunk_000.pak` instead would avoid the game entirely, but
the assets in there are MurmurHash-named `.user.2` blobs, and MMDK's real value
is the object → JSON conversion that `extract-geometry.mjs` already assumes.
Rebuilding that is a project, not a shortcut.

The wizard automates everything either side of the human part:

```
bash refresh-dump.sh          # generated by the /wizard skill; ephemeral
```

It installs REFramework and MMDK on the Windows box over SSH, waits while you
dump one character in-game, pulls the JSON back into a tree beside the pinned one,
and runs the diff. Set `CHAR=Mai` to do a different fighter.

## The diff

```
MMDK_RAW=data/raw/mmdk GEOMETRY_OUT=/tmp/fresh \
  node scripts/extract-geometry.mjs Ryu
node scripts/diff-geometry.mjs data/geometry/ryu.json /tmp/fresh/ryu.json
```

`extract-geometry.mjs` honours `MMDK_RAW` and `GEOMETRY_OUT` precisely so a
second dump can be extracted beside the pinned one without disturbing it.

`diff-geometry.mjs` compares the **extracted artifact**, not the raw dump. Ryu's
`moves_dict` alone is 8.6 MB of mostly-cosmetic keys; the extracted file is the
subset the engine consumes, so anything the diff reports is something that can
change an answer. It looks at action lengths and `MarginFrame`, hit-key windows,
projectile launch speed, the outcome table's damage/stun/`DownTime`/`DmgType`/
`DmgRecover`, and which action each notation maps to.

## The whole-tree audit

The per-character diff above says *what moved*. To find out whether any of it
**matters to a percentage**, grade both trees row by row:

```
npm run geometry:2024                                   # rebuild the old tree
node scripts/skew-audit.mjs /tmp/geometry-2024 data/geometry
```

It reports, per check, how many rows moved, how many the newer tree fixes and how
many it breaks — and names every moved row. As of
[ADR-0045](../adr/0045-the-dump-is-the-live-game-now.md) the answer over the full
24-fighter roster is **+0.6 points overall, +0.7 on the clean population**: 92 of
the clean population's 580 disagreements are skew and 488 are ours. Skew is a real
confound and a small one, and 49 rows run the other way, which is FAT lagging the
game rather than the dump lagging FAT.

## Reading the result

**No changes** — version skew is dead as an explanation for that character, and
every disagreement it has is ours. Say so in the next ADR; it retroactively
strengthens every percentage in the project.

**Changes** — note which fields moved before trusting any check that reads them.
A `move -> action` change is the loudest possible signal: it moves every check
for that move at once.

Either way both trees stay on disk (gitignored) and
`data/geometry/` is untouched, so both readings remain side by side.

## Do not silently re-pin

Replacing the snapshot wholesale re-baselines every number in every ADR in one
commit, with no way to tell which moved because the game changed and which moved
because the reading changed. Diff first, one character at a time, and record
what moved. That is what ADR-0043's audit and ADR-0045 are: the re-pin happened
*after* every row had been graded both ways, and the ADR names what moved. Do the
same next time.
